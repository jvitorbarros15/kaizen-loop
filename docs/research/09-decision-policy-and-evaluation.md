# Decision thresholds, guardrails, token economics and release tests

This companion to the [loop architecture](08-self-improving-agent-architecture.md) specifies how to choose an operating point and determine whether a Jev-like model improves an agent. Numerical examples are illustrative unless attributed to a study.

## Choose the question before choosing the threshold

A Choice over skills measures which available option best fits. A binary fit question addresses whether the catalog contains an applicable skill. A policy question asks whether one criterion applies to a proposed action. A verifier checks whether the resulting artifact satisfies a task. Each needs different labels. Training a risk gate on “the worker eventually succeeded” teaches it that a policy violation can be acceptable if the tests still pass.

For Choice and Score, TypeSafe exposes option or level probabilities plus a derived confidence statistic. For a fixed-size Choice, the confidence value is a transformation of the top probability. Counting both as separate votes double-counts evidence. Inspect the runner-up and the candidate-set size, and calibrate the actual event that triggers action. A Noul returns a value for a yes/no proposition. A Score can hide uncertainty between distant levels, so inspect the level probabilities when a high-severity category matters. [TypeSafe confidence reference](https://docs.typesafe.ai/confidence) · [Probability routing](https://docs.typesafe.ai/patterns/probability-routing)

For a binary routing example, let p be the locally calibrated chance the proposed route is correct. If a wrong automatic route costs 20 units and independent resolution costs 2 units and is perfect, acting directly has expected loss 20 × (1 − p). It beats resolution when p exceeds 0.90. If review also makes errors, takes longer during peak loads, or carries its own operating cost, include each term in expected loss. Treat hard authorization constraints as constraints on the available actions before applying this calculation. A posterior preference cannot grant authority.

Estimate calibration on a held-out, labeled calibration split. Plot observed correctness against predicted probability, report Brier score and per-route sample counts, and inspect high-confidence errors individually. For a multi-class Choice, the Brier score is the average sum of squared differences between the option probabilities and one-hot labels. Report the formula and normalization. Temperature scaling is one inexpensive baseline when logits are available. Calibrate per version and inspect relevant slices such as tool family, language, novel repo, missing context, and option count. [Guo et al. on calibration](https://arxiv.org/abs/1706.04599)

Sweep the threshold and plot **coverage** (fraction of eligible decisions taken automatically) against **selective risk** (fraction wrong among those decisions). Also report how many bad actions were allowed among *all actual violations*. A gate can have excellent overall accuracy while missing rare high-impact cases. Choose thresholds on the calibration split, freeze them, then score the final split. Conformal prediction sets can support returning several plausible options under suitable exchangeability assumptions. A changing repository or policy can break those assumptions. [Selective classification](https://arxiv.org/abs/1705.08500) · [Conformal prediction tutorial](https://arxiv.org/abs/2107.07511)

## Guardrails the runtime can actually enforce

| Boundary | Trusted inputs | Decision-model role | Binding behavior |
| --- | --- | --- | --- |
| Task admission | Authenticated caller, granted scope and configured capabilities | Classify unclear task intent | Controller selects an eligible workflow or requests clarification |
| Context loading | Source identity, access rights, repository revision | Rank relevant evidence and flag questionable material | Retrieval layer enforces access and preserves provenance |
| Before tool execution | Normalized arguments, destination, operation class, current permissions | Screen semantic mismatches between the request and proposed action | Executor enforces hard constraints, routes uncertain protected actions for review, and revalidates before execution |
| Before releasing output | Artifact type, actual destination, trusted redaction rules | Screen draft output against explicit content rules | Apply deterministic checks and hold material requiring review |
| Before persistent updates | Candidate diff, locked evaluation results and approved change scope | Triage proposed lessons or summarize discrepancies | Independent release process controls persistent policy, permission, grader and model updates |

Write each semantic rule with a scope, triggering facts, exclusions, positive and near-boundary negative examples, and the prescribed fallback. For example, a project policy might permit generating release notes in a checkout while requiring an explicit grant to publish them. A classifier can distinguish the intent expressed in prose. The executor can directly check the destination, operation and grant. Include paired fixtures that differ only in local generation versus publication. Include cases with missing destination or missing evidence as a third outcome. Keep raw untrusted content inside a labeled data field, with trusted policy supplied independently.

A November 2026 preprint tested 22 decision models and two prompted general models on 2,643 synthetic tool calls against 28 rules. In the reported Jev 1.14 comparison, explicit boundary examples raised recall from 89.3% to 98.2% and reduced unnecessary interruptions from 30.6% to 4.8% on 252 clean actions. The synthetic cases and shared preamble matter when interpreting these numbers. Another study of decision judges found substantial model-to-model variation in verdict stability under extraneous instructions. Both results favor measuring misses and false interruptions with the exact deployed question and policy. [Policy-gate study](https://arxiv.org/abs/2611.02155) · [Decision-judge study](https://arxiv.org/abs/2611.00505)

**Failure behavior depends on the role.** An optional skill selector can time out and return the ordinary worker path. A required protected-action check can time out and hold the action. A full review queue must have an explicit waiting or cancellation state so queue pressure cannot silently change the policy. Record the final decision and reason. Cache a reusable decision only with a key that includes the exact state, candidate set, policy and model versions, permission scope and destination as applicable. Always recheck current authority and mutable state when executing.

**Guardrail metrics.** Report false allowances by rule and severity, false interruptions on clean actions, abstention rate, reviewer overturn rate, check latency, and protected actions that actually passed through the control point. A classifier can achieve perfect fixture recall while an unmediated tool path bypasses it entirely. Include alternate entry points, background operations, missing telemetry and checker timeouts in integration tests. If zero misses occur on N independent representative positive cases, an approximate one-sided 95% upper bound on miss rate is 3/N. Zero misses in 100 examples still leaves room for roughly a 3% miss rate. Clustered cases supply less independent evidence.

## Count tokens at the boundary where savings occur

Use three ledgers. **Worker tokens** count all Claude or Codex roles, including retries, evaluators and nested workers. **Decision usage** counts hosted decision charges or local encoder input, compute and wall time. **End-to-end economics** sums actual costs for both, plus verification and amortized training or optimization when relevant. Providers can expose different token definitions and billing units. Keep raw usage per provider. A router that emits a number can still process a long input on every call. Reuse stable prompt prefixes where supported and measure cache hits independently. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) · [Claude Code costs](https://code.claude.com/docs/en/costs)

**Worked example.** In 100 tasks a baseline uses 100,000 worker input tokens and 20,000 output tokens. A selector avoids 30,000 input tokens, but fallback reads add back 8,000 and retries add 2,000 output tokens. Worker usage becomes 78,000 input plus 22,000 output, saving 20,000 worker tokens, or 16.7%. If the decision endpoint reads 25,000 additional tokens across those tasks, the combined count rises to 125,000 under a comparable tokenizer. Dollars may still fall if that compute is cheaper. Conversely, removing already cached prefix tokens can save less money than the raw count implies. Use actual billing for each route.

For a gate placed before an expensive operation, define q as the fraction of opportunities that avoid it, D as average decision cost on every opportunity, V as the mean avoided cost on the skipped subset, and R as the incremental expected cost per opportunity of fallback, rework and verification. The expected saving per opportunity is qV − D − R. With D = $0.001, V = $0.02 and R = $0.002, break-even requires q above 15%. Calculate these quantities on the same traffic mix. If expensive tasks are less likely to be skipped, using the mean baseline call cost for V exaggerates savings.

**Two-stage skill selection.** TypeSafe's cookbook ranks 194 skill descriptors and checks the top three with richer information, allowing rejection of every option. This is a documented implementation pattern. For Claude or Codex, compare it to the actual client with native skill discovery, then to lexical retrieval and a single decision pass. Record baseline descriptors already in the worker prompt, extra selector requests, whether the chosen body would have been loaded anyway, and whether a missing skill causes rereads. Where a cheap first pass reliably handles easy cases, invoke the second pass only on ambiguous cases. Batch same-state independent questions when latency dominates. Sequential screening can be cheaper when most inputs stop early. [TypeSafe skill cookbook](https://docs.typesafe.ai/cookbooks/skill_suggestion) · [Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out) · [Noul screening](https://docs.typesafe.ai/patterns/noul-screen)

**Context management baseline.** Try removing obsolete tool output while preserving artifact pointers before paying a model to rewrite every trace. JetBrains researchers found simple observation masking competitive with LLM summarization on the studied agent settings. SWE-Pruner supplies a separate task-aware line-selection baseline. Evaluate failures on exact identifiers and dependent code spans, and count subsequent file reads. [Observation masking study](https://arxiv.org/abs/2508.21433) · [SWE-Pruner](https://arxiv.org/abs/2601.16746)

## Evaluation design that can distinguish improvement from extra attempts

| Arm | Enabled features | Question answered |
| --- | --- | --- |
| A | Standard client and its normal skills, fixed budget | What does the existing workflow achieve? |
| B | Same worker plus deterministic retrieval, output trimming and verified retries | How much can orchestration alone achieve? |
| C | B plus a Jev-like skill selector | Does learned selection add value over inexpensive retrieval? |
| D | C plus reviewed lessons from disjoint training tasks | Does durable experience help on fresh tasks? |
| E | D plus semantic screening alongside the same hard controls | How much incremental guardrail coverage and friction does screening add? |
| F | E with an alternative local decision model or cheap generative classifier | Does deployment choice change the quality, latency and cost trade-off? |

Hold the base model, max attempts, cache profile, tool inventory and task set constant within provider. Use additional paired ablations where interactions matter, for example C with and without a second ranking pass, D with and without selected lessons on the same tasks, and B with the guardrail to isolate the effect before learning. Keep binding controls active in compared arms. Use simulated executions for known policy-violation fixtures. Split by repository or by time before constructing examples and keep private acceptance checks and final tasks outside the optimizer. Repeat stochastic trials, randomize arm order and report paired uncertainty intervals clustered by repository. Count unsolved, timed-out and interrupted tasks under a stated denominator.

Historical replay sees the consequence of the chosen route. A log from a deterministic controller contains no outcomes for alternatives it never tried. Shadow scoring measures disagreement, latency and decision coverage. It cannot establish the causal effect of the alternative on verified solves. Replay both branches in isolated copies for cheap reversible actions, or randomize among authorized, comparable alternatives during a limited trial. If using off-policy estimators, log action selection probabilities and check support and weight variance. Contextual-bandit estimators address single-step feedback under specific assumptions. Repeated tool choices also change later states, making whole-task paired trials especially important. [Doubly robust policy evaluation](https://arxiv.org/abs/1103.4601)

**Release decision.** Predeclare a maximum acceptable loss in verified solve rate, guardrail miss bounds by severity, review capacity, and minimum economic benefit. Report first-attempt solve rate, solve-within-budget, total dollars per verified solve, worker tokens per verified solve, p95 task latency and each guardrail metric. Compute cost per solve as total spend on all trials divided by verified successes, retaining failed-trial costs. If intervals cannot resolve the quality margin or a critical policy slice has too few cases, keep that route in shadow or review and continue collecting labels. A useful first release is a reversible skill selector whose benefit survives the baseline comparison. Expand one decision point at a time so regressions can be traced to a specific intervention.
